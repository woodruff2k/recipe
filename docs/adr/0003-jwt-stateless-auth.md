# ADR-0003: JWT 기반 무상태 인증

## 상태

Accepted

## 컨텍스트

로그인 이후 사용자를 식별하고 보호된 API(레시피 작성/수정/삭제, 프로필 등)에 대한
접근을 제어할 방법이 필요했다. Express 서버는 상태를 서버 메모리나 별도 세션
저장소에 두지 않는 단순한 구조를 목표로 했다.

## 결정

로그인/회원가입 성공 시 **JWT**를 발급하고(`utils/jwt.ts`의 `signToken`), 클라이언트가
이후 요청마다 `Authorization: Bearer <token>` 헤더로 전달한다. 서버는
`middlewares/auth.ts`의 `requireAuth`가 토큰을 검증해 `req.userId`를 채우는 것으로
끝난다 — 세션 저장소나 서버 측 상태가 전혀 없다. 프론트엔드는 토큰을
`localStorage`(`lib/api.ts`의 `tokenStore`)에 보관한다.

## 고려했던 대안

| 대안                                       | 기각 사유                                                                                                                                                                                                                        |
| ------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **세션 + 쿠키**(express-session, Redis 등) | 세션 저장소(Redis 등) 운영 부담이 추가되고, 서버를 무상태로 유지하려는 목표와 어긋남. 다중 인스턴스로 스케일할 때 세션 동기화 문제도 없앨 수 있어 JWT가 이 규모의 프로젝트엔 더 단순함                                           |
| **httpOnly 쿠키에 JWT 저장**               | XSS로부터 토큰을 더 안전하게 보호할 수 있다는 장점이 있으나, CSRF 대응(SameSite/CSRF 토큰)이 추가로 필요해지고 CORS 설정이 더 복잡해짐(백엔드/프론트가 다른 포트·오리진). 학습 목적상 `Authorization` 헤더 방식이 더 명료해 채택 |
| **OAuth/소셜 로그인 전용**                 | 이메일/비밀번호 자체 인증 흐름(해싱, 검증)을 다루는 것이 이 프로젝트의 학습 목표 중 하나라 기각. 소셜 로그인은 이후 별도로 추가 가능한 영역으로 남김                                                                             |
| **NextAuth.js(Auth.js)**                   | 프론트엔드가 Next.js라 자연스러운 선택지였으나, 인증 로직이 프론트엔드에 종속되고 별도 Express API가 독립적으로 인증을 검증할 수 없게 됨. 백엔드가 인증의 단일 진실 공급원(source of truth)이어야 한다는 설계와 맞지 않아 기각   |

## 결과 (Consequences)

**긍정적**

- 서버가 완전히 무상태라 수평 확장이 단순함(세션 동기화 불필요)
- 인증 로직이 백엔드에 집중되어 있어, 향후 모바일 앱 등 다른 클라이언트를 추가해도 같은 `/api/auth` 엔드포인트를 그대로 재사용 가능
- 토큰 발급/검증이 `utils/jwt.ts` 한 곳에 모여 있어 테스트하기 쉬움(실제로 `jwt.test.ts`에서 정상/malformed 토큰 케이스를 커버)

**트레이드오프**

- **토큰 무효화(로그아웃)가 서버 측에서 불가능**하다 — 클라이언트가 `localStorage`에서 토큰을 지우는 것으로만 "로그아웃"이 구현되어 있어, 탈취된 토큰은 만료 시점(`JWT_EXPIRES_IN`, 기본 7일)까지 유효하다. 실제 서비스라면 블랙리스트/짧은 만료+리프레시 토큰 전략이 필요
- `localStorage`에 토큰을 저장하는 방식은 httpOnly 쿠키보다 XSS에 더 취약함 — 이 프로젝트는 신뢰할 수 있는 프론트엔드(자체 개발) 전제로 리스크를 감수한 선택
- 비밀번호 재설정(US-1.7, 아직 미구현)처럼 "토큰을 즉시 무효화해야 하는" 요구사항이 생기면 현재 구조로는 추가 설계(예: 토큰 버전 필드)가 필요함
