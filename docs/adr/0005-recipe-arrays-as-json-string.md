# ADR-0005: Recipe 배열 필드를 JSON 문자열로 저장

## 상태

Accepted (기술 부채로 인지, 재검토 대상)

## 컨텍스트

레시피의 `ingredients`(재료)와 `steps`(조리 순서)는 본질적으로 문자열 배열이다.
[ADR-0002](./0002-postgresql-over-sqlite.md)에서 다뤘듯 이 프로젝트는 원래
**SQLite**로 시작했고, SQLite에는 네이티브 배열/JSON 컬럼 타입이 없다. 그래서 두
필드를 `JSON.stringify`한 문자열로 저장하고, 읽을 때 다시 파싱하는 방식을 택했다.

## 결정

`schema.prisma`에서 두 필드를 `String @default("[]")`로 선언한다. 쓰기 시
`recipe.controller.ts`가 `JSON.stringify(data.ingredients)`로 직렬화하고, 읽기 시
`safeParseArray()`(파싱 실패하면 빈 배열로 폴백)로 역직렬화해 API 응답에서는
정상적인 배열로 노출한다. Postgres로 전환한 뒤에도 **이 방식을 그대로 유지**했다
— 스키마 컬럼 타입을 바꾸지 않고 provider만 바꾸는 것이 전환 리스크가 가장 작은
경로였기 때문이다.

## 고려했던 대안

| 대안                                                       | 기각 사유(당시) / 재검토 시 고려사항                                                                                                                                                                                                              |
| ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Postgres 전환 시 `Json` 타입으로 마이그레이션**          | 전환 당시엔 "동작하는 것을 최대한 안 건드리고 provider만 바꾼다"는 원칙으로 범위를 좁혀 기각. 재검토한다면 `Json` 타입은 Prisma가 자동으로 파싱해주므로 `safeParseArray`/`JSON.stringify` 호출을 컨트롤러에서 전부 제거할 수 있어 코드가 단순해짐 |
| **Postgres `text[]`(네이티브 배열)**                       | `Json`보다 더 타입에 가깝지만(요소가 항상 string임이 DB 레벨에서 보장됨), Prisma의 배열 타입 지원과 마이그레이션 도구 성숙도가 `Json`보다 다소 떨어져 초기엔 `Json` 쪽이 더 안전한 선택으로 보임                                                  |
| **별도 테이블로 정규화**(`Ingredient`, `Step` 테이블, 1:N) | 재료에 수량/단위 같은 구조화된 정보를 담거나, 재료 기준 검색(예: "토마토 들어간 레시피")이 필요해지면 정규화가 맞다. 현재 요구사항(단순 텍스트 목록 표시)에는 과설계라 기각. 향후 US 확장 시 재검토                                               |

## 결과 (Consequences)

**긍정적**

- Postgres 전환 시 컨트롤러 로직을 거의 건드리지 않아 마이그레이션 리스크가 작았음
- `safeParseArray`가 파싱 실패를 빈 배열로 폴백해, 손상된 데이터가 있어도 API가 500을 내지 않고 방어적으로 동작함(실제로 `recipe.controller.test.ts`에 이 폴백을 검증하는 테스트가 있음)

**트레이드오프 (기술 부채)**

- **DB 레벨에서 재료/순서 내용으로 검색·필터링이 불가능**하다 — 문자열 하나로 저장되어 있어 SQL로 배열 요소를 조회할 수 없음. 현재 검색(`US-3.3`)은 `title`/`description`에만 적용되고 `ingredients`는 대상이 아닌 이유가 바로 이것
- 매 요청마다 `JSON.stringify`/`JSON.parse`를 거쳐야 해서 미미하지만 불필요한 CPU 비용이 있음
- Prisma의 타입 안전성이 이 두 필드에는 적용되지 않음(스키마상 `String`이라 배열이라는 사실이 타입 레벨에 드러나지 않고, 컨트롤러의 수동 변환에 의존)
- **재검토 시점**: `US-3.5`(카테고리/태그 필터)처럼 배열 내용 기반 쿼리가 필요한 기능이 실제로 요구되면, 이 ADR을 `Superseded`로 바꾸고 `Json` 타입 마이그레이션을 진행해야 한다
