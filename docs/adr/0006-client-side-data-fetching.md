# ADR-0006: 클라이언트 사이드 데이터 페칭 (Server Components 미사용)

## 상태

Accepted

## 컨텍스트

Next.js 14 App Router는 서버 컴포넌트에서 직접 `fetch`하는 방식(RSC 데이터 페칭)을
기본으로 권장한다. 하지만 이 프로젝트의 백엔드는 별도 Express 서버이고, 인증은
JWT를 `localStorage`(브라우저 전용 API)에 저장하는 방식([ADR-0003](./0003-jwt-stateless-auth.md))을
택했다. 서버 컴포넌트는 브라우저의 `localStorage`에 접근할 수 없다.

## 결정

거의 모든 페이지를 `"use client"` 컴포넌트로 만들고, `useEffect` 안에서
`lib/api.ts`의 `api` 객체를 통해 데이터를 가져온다. `api.ts`가 `tokenStore`에서
토큰을 읽어 `Authorization` 헤더를 자동으로 채워준다. 컴포넌트에서 직접 `fetch`를
부르지 않고 항상 이 클라이언트를 거치도록 강제한다(`CLAUDE.md` 규칙).

## 고려했던 대안

| 대안                                       | 기각 사유                                                                                                                                                                                                                                                                                  |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Server Components + 서버 사이드 fetch**  | JWT가 `localStorage`에 있어 서버 컴포넌트 렌더링 시점(요청-응답 사이클의 서버 쪽)에는 토큰에 접근할 수 없음. httpOnly 쿠키로 토큰을 옮기면 가능해지지만, 그건 [ADR-0003](./0003-jwt-stateless-auth.md)에서 이미 기각한 경로 — 인증 방식을 바꾸지 않는 한 이 대안은 성립하지 않음           |
| **httpOnly 쿠키 인증 + Server Components** | 가장 "Next.js다운" 방식이지만, CSRF 대응과 CORS 설정이 추가로 필요해지고, Express 백엔드가 Next.js의 쿠키 규약에 맞춰야 하는 결합이 생김. 프론트/백엔드 독립성([ADR-0001](./0001-monorepo-pnpm-workspace.md)의 모노레포 안에서도 두 앱을 분리 배포 가능하게 유지하려는 목표)과 상충해 기각 |
| **React Query / SWR 도입**                 | 캐싱·재검증·낙관적 업데이트 등 데이터 페칭의 부가 기능을 얻을 수 있지만, 이 프로젝트 규모(페이지당 API 호출 1~2개, 복잡한 캐시 무효화 요구 없음)에서는 `useEffect` + 자체 로딩/에러 상태로 충분하다고 판단. 의존성을 하나 더 늘리는 비용이 이득보다 크다고 봄                              |

## 결과 (Consequences)

**긍정적**

- 인증 방식(localStorage JWT)과 데이터 페칭 방식이 서로 모순 없이 맞아떨어짐
- 모든 API 호출이 `lib/api.ts` 한 곳을 거쳐 토큰 주입·에러 변환(`ApiError`)·FormData 처리가 일관됨
- 서버 컴포넌트/클라이언트 컴포넌트 경계를 신경 쓸 필요가 거의 없어 학습 곡선이 낮음(하이드레이션 불일치 등 RSC 특유의 함정을 피함)

**트레이드오프**

- Next.js App Router의 핵심 이점(서버에서 미리 렌더링해 초기 로딩 체감 속도를 높이는 것)을 거의 활용하지 못함 — 모든 페이지가 "빈 화면 → 로딩 중... → 데이터 렌더" 흐름을 거침(실제로 각 페이지에 `if (loading) return <p>불러오는 중...</p>` 패턴이 반복됨)
- SEO가 중요한 서비스라면 불리함(레시피 상세 페이지가 검색엔진에 빈 셸로 보일 수 있음) — 이 프로젝트는 로그인 기반 서비스라 SEO 우선순위가 낮아 수용 가능한 트레이드오프로 판단
- 각 페이지가 로딩/에러 상태를 개별적으로 관리해 코드가 일부 반복됨(`useState` 세 개 + `useEffect` 패턴이 페이지마다 유사하게 나타남) — 페이지 수가 늘면 공통 훅(`useApiQuery` 같은)으로 추출을 고려할 만함
