# ADR-0001: pnpm workspace 모노레포 구조

## 상태

Accepted

## 컨텍스트

`backend`(Express API)와 `frontend`(Next.js)는 별개로 배포되는 두 애플리케이션이지만,
공유 타입(`Recipe`, `User` 등의 API 계약)과 개발 도구(TypeScript, Prettier, Git hooks)를
공통으로 관리해야 한다. 두 앱을 어떻게 묶어 개발할지 결정이 필요했다.

## 결정

**pnpm workspace**로 단일 저장소(`recipe/`) 안에 `backend/`, `frontend/`를 워크스페이스
패키지로 묶는다. 공유 버전(`typescript`, `@types/node`)은 `pnpm-workspace.yaml`의
`catalog:` 기능으로 한 곳에서 관리한다. 루트 `package.json`은 워크스페이스 전체를
다루는 스크립트(`pnpm -r build`, `pnpm --parallel -r dev` 등)만 갖고, 실제 런타임
의존성은 각 패키지에 격리한다.

## 고려했던 대안

| 대안                                             | 기각 사유                                                                                                                                                                                                                                             |
| ------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **별도 저장소 2개**(backend-repo, frontend-repo) | API 계약이 바뀔 때 PR을 두 저장소에 나눠 올려야 해서 리뷰·버전 동기화 비용이 큼. 이 프로젝트 규모(1인 개발, 소규모 팀)에서는 이점보다 오버헤드가 큼                                                                                                   |
| **npm/yarn workspace**                           | 기능은 비슷하지만 `catalog:` 같은 버전 단일화 기능이 없거나(npm) 별도 설정이 더 필요함(yarn). `packageManager: pnpm@9.15.9`로 이미 pnpm을 채택한 상태에서 굳이 바꿀 이유 없음                                                                         |
| **Turborepo / Nx**                               | 빌드 캐싱·태스크 그래프 최적화가 강점이지만, 패키지가 2개뿐인 규모에서는 설정 복잡도 대비 이득이 작음. 워크스페이스가 3개 이상으로 늘거나 빌드 시간이 병목이 되면 재검토 대상                                                                         |
| **단일 Next.js 앱**(API Routes로 백엔드 흡수)    | Express 고유의 미들웨어 체인(`asyncHandler`, 중앙 에러 핸들러)과 별도 배포 단위(Express는 상시 실행 서버, Next.js는 서버리스/standalone 어느 쪽으로도 갈 수 있음)를 유지하고 싶어 기각. 학습 목적상 프론트/백엔드 경계를 명확히 두는 것도 의도적 선택 |

## 결과 (Consequences)

**긍정적**

- 의존성 버전 불일치(TypeScript 버전 드리프트 등)가 `catalog:` 덕분에 원천 차단됨
- `pnpm --filter ./backend <cmd>`로 개별 패키지 명령을 실행하면서도 루트에서 전체 lint/typecheck/test를 한 번에 돌릴 수 있음(`pnpm -r`)
- Git hooks(`(.husky/`)를 저장소 하나에만 두면 되어 CI/로컬 훅 설정이 단순함

**트레이드오프**

- `corepack enable`을 하지 않으면 `pnpm: command not found`가 나는 등, pnpm 고유의 설정 단계가 하나 더 필요함(실제로 이 프로젝트 개발 중 여러 번 겪은 문제 — [`GETTING-STARTED.md`](../GETTING-STARTED.md) 참고)
- 두 앱이 한 저장소에 있어 “백엔드만 릴리스”, “프론트만 릴리스”처럼 독립 배포 이력을 깔끔히 분리하기 어려움(현재는 모노레포 전체가 한 번에 태그/배포됨)
- 워크스페이스가 커지면(3개 이상) Turborepo/Nx 없이는 빌드 캐싱 이점을 못 봄 — 현재 규모에서는 문제 아님
