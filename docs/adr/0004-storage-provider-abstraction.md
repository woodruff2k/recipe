# ADR-0004: StorageProvider 추상화 (S3 전환 대비)

## 상태

Accepted

## 컨텍스트

레시피 대표 이미지를 업로드·저장해야 한다. 로컬 개발/소규모 배포에서는 서버
파일시스템에 직접 저장하는 게 가장 간단하지만, 실제 운영 환경(다중 인스턴스,
컨테이너 재시작 시 파일 유실)에서는 S3 같은 오브젝트 스토리지가 사실상 필수다.
두 요구사항(지금 당장의 단순함 vs. 향후 확장성)을 동시에 만족시킬 방법이 필요했다.

## 결정

`storage/StorageProvider.ts` 인터페이스(`save`, `delete`)를 정의하고, 애플리케이션
코드(`upload.controller.ts`)는 이 인터페이스에만 의존한다. 구현체 선택은
`storage/index.ts`의 팩토리가 `STORAGE_DRIVER` 환경변수로 결정한다. 현재는
`LocalStorageProvider`만 구현되어 있고, `s3` 값이 오면 `throw`(미구현 명시)한다.

```ts
switch (env.storageDriver) {
  case "s3":
    throw new Error(
      "STORAGE_DRIVER=s3 is not implemented yet. Add S3StorageProvider in src/storage.",
    );
  case "local":
  default:
    return new LocalStorageProvider();
}
```

## 고려했던 대안

| 대안                                                            | 기각 사유                                                                                                                                                                                                                                                                                 |
| --------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **처음부터 S3만 지원**                                          | 로컬 개발 시 AWS 계정·자격증명 없이는 이미지 업로드 기능을 테스트할 수 없게 됨. 학습/데모 환경의 진입 장벽을 불필요하게 높임                                                                                                                                                              |
| **로컬 파일 저장만 하고 추상화 없이 하드코딩**                  | 당장은 더 간단하지만, 실제로 S3로 전환할 시점에 `upload.controller.ts`를 포함해 파일 저장을 호출하는 모든 지점을 찾아 고쳐야 함. `StorageProvider`처럼 인터페이스를 먼저 만들어두면 팩토리 분기 한 줄만 바꾸면 되므로, 미리 드는 비용(인터페이스 설계)이 나중에 아낄 비용보다 작다고 판단 |
| **멀티 클라우드 추상화 라이브러리**(예: unstorage, flysystem류) | 이 프로젝트가 지원해야 하는 백엔드가 local과 S3 단 둘뿐이라, 범용 라이브러리의 기능 대부분이 쓰이지 않음. 직접 만든 2-메서드 인터페이스가 더 명료하고 의존성도 하나 줄어듦                                                                                                                |

## 결과 (Consequences)

**긍정적**

- S3 전환 시 변경 범위가 명확함: `S3StorageProvider` 구현체 추가 + 팩토리 분기 한 줄. 컨트롤러·라우트는 무수정
- 로컬 개발은 AWS 계정 없이 즉시 동작(`STORAGE_DRIVER=local`이 기본값)
- 인터페이스가 2개 메서드(`save`/`delete`)로 작아 테스트하기 쉬움(`LocalStorageProvider.test.ts`가 실제 파일시스템에 대해 저장/삭제/MIME 매핑을 검증)

**트레이드오프**

- `S3StorageProvider`는 아직 미구현 상태(throw만 함) — 이 추상화가 "실제로 값어치를 증명"하려면 최소 한 번은 S3 구현체를 추가해봐야 하는데, 현재는 설계만 있고 검증되지 않은 가정 위에 있음. 실제 구현 시 `save`/`delete` 시그니처가 S3의 실제 필요(예: presigned URL, 멀티파트 업로드)에 안 맞아 인터페이스를 수정해야 할 가능성 존재
- 로컬/S3 사이의 세부 동작 차이(예: `delete`의 idempotency, 파일 접근 URL의 만료 여부)를 인터페이스가 완전히 추상화하지 못할 수 있음 — 구현 시 재검토 필요
